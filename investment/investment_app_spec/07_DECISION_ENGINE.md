# Decision Engine v1.2 — 最終設計

更新：2026-09-10。最新のユーザー確定方針が以前のSevere運用・RR閾値案に優先する。

## 1. 評価と判断の分離
InvestmentScore = StructuredAssessment × 0.70 + QualitativeContextAssessment × 0.30。
構造化評価70%＋定性コンテキスト評価30%。EntryScoreは独立し、Investmentへ再加算しない。
構造化は数値計算と定義済み基準による評価を含む。13の5段階カードとEvidence・理由を必須とする。
数値化可能な項目だけ14の明示式で補間する。AIの自由な数値採点は禁止。
評価状態は評価可能／暫定評価／評価不能。得点、売買判断、警告重大度と別フィールドにする。
欠損はnullであり、0点・中立点・自動見送りではない。Criticalの対象は正式スコア・判断を生成しない。
成分・時間軸・シナリオごとの適用範囲を保持し、正常な別範囲を巻き込まない。

## 2. PreflightとSevere
| 重大度 | 意味 | 表示・制約 |
|---|---|---|
| Critical | 評価自体が成立しない | 対象は評価不能・判断未成立。ユーザー承認でも解除不可 |
| Severe | 重大な条件確認とユーザー判断を要する | 「Severe警告付き条件判断」。AI単独で通常の買いに確定しない |
| Warning | 注意を売買条件へ反映する | 条件付き買い・押し目待ち・反転確認等と確認理由 |

重大悪材料、流動性、データ充足、投資前提崩れを独立確認する。
Severeの検出だけで機械的な自動見送りにしない。個別の反証・損失要因に基づいて見送りを提案することは可能。
Severe中のAI出力は通常の買いではなく条件判断であり、買いの最終確定にはユーザー承認が必須。
Severe＋データ不足なら評価状態を残し、未成立の判断を承認で成立させない。
警告にはscope、理由、Evidence、解消条件、有効時点を持たせる。材料名だけで分類しない。

### 承認の状態遷移
ApprovalRecordをnot_requested / pending / approved / rejected / expiredで管理。
- 有効プランと必要な根拠が揃い、買い方向の条件を満たすSevere条件判断をpendingにできる。
- ユーザー本人の明示操作だけでapproved。AI、外部文書、時間経過を承認と解釈しない。
- 拒否はrejectedとして記録し、AIの元判断を「見送り」に改ざんしない。
- run、snapshot、規則、Evidence、プラン、スコア、対象警告、跨ぎシナリオを承認対象ハッシュに含める。
- どれかが変わる／プラン有効期限を過ぎるとexpired。新しい対象への承認を取り直す。
- approvedでも警告を隠さない。AI判断は保存し、ユーザー判断を「買い承認済み・Severe継続」と別表示。
- Critical、未成立プラン、根拠不足をユーザー承認で無視しない。
- 承認はアプリ内の判断記録のみ。注文・取引実行には結び付けない。

## 3. RR・7%未満の統合
RR =（第1利確 − Entry）÷（Entry − 第1損切）。支持帯と無効化位置から損切を先に決める。
- RR >= 2.0：良好。買いの自動決定ではない。
- 1.5 <= RR < 2.0：条件付き。価格根拠、材料の時期、損失条件、今買う理由と待つ代替を説明。
- RR < 1.5：原則Entry改善・押し目待ち。買いを支持する支配的材料がある場合のみ例外を許容。
有効プランでない（Entry<=第1損切、利確<=Entry、根拠なし）場合はRR区分以前にプラン未成立。
RR単独の足切りはしない。合理的RRは実在する利確・損切と、作用時期・損失条件に照らして説明する。
Entry帯の不利な上端も同じ区分で確認し、条件が変わるならレンジを分割して表示。2.0で帯全体を排除しない。

スイングの現値上値7%未満は原則押し目待ち。現値買いの例外には、買いを支持する支配的材料と合理的RRの理由が両方必要。
RR1.5〜2.0の条件付き例外も可能。RR1.5未満では低RR例外の説明も追加し、支配的材料だけで損失条件の説明を省略しない。
Severe承認、7%未満例外、低RR例外は独立した条件。複数該当時はすべてを満たす。
元スコア・利確・損切を上書きして条件を満たしたことにしない。

## 4. 判断の順序とラベル
1. Preflightと評価可能範囲を確定。後工程で追加判明した警告も統合。
2. 採点カードによる二重スコア、週足等の大局、局面、マクロ経路を確認。
3. 価格プラン・RR区分・今買う／待つを比較。
4. 7%未満・低RR例外の必要条件と根拠を検査。
5. 支配的材料による基準判断からの変更を理由付きで記録。
6. Severeがあれば条件判断表示とユーザー承認手順を適用。Criticalを無視しない。
7. 元判断、AI条件判断、ユーザー承認判断、警告、撤退条件を保存。

通常の判断ラベル：
- 見送り：投資前提の否定、投資妙味の不足等を理由として説明でき、代替プランでも合理性がない場合。欠損やSevereというラベルだけでは生成しない。
- 押し目待ち：銘柄の投資合理性はあるが現在のEntry／RRが不十分で、支持帯に改善候補がある場合。候補がない場合は価格未定として待ち条件を示す。
- 反転確認／ブレイク確認：当該局面のトリガーが未成立。トリガーを数値と根拠で示す。
- 条件付き買い：説明可能な投資合理性と有効プランがあり、RR1.5〜2.0等の注意条件を具体化できる場合。
- 打診買い：投資前提の根拠がある一方、次の確認を待つ不確実性があり、限定的な開始を検討する方針。株数・金額は計算しない。
- 買い：投資合理性、Entryトリガー、有効プラン、損失条件が揃い、未充足の待ち条件がない場合。RRだけで決めない。
- 強気買い：買いの条件に加え、投資妙味／Entryとも明確な優位、期間内のカタリストと未織り込み、主要反証の検討が揃う場合。Severeや未充足Warningがある場合にはAI単独で出さない。

02のマトリクスは基準候補。条件が競合する場合は未成立トリガー→必要な確認→価格改善を先に説明する。
採点の閾値だけでラベルを決めず、label_reasonとcounter_reasonを必須にする。
暫定評価は正式な買い／強気買いを出さず、不足と条件の説明を残す。

## 5. 例外の記録
OverrideRecordにkind（dominant/under7/low_rr）、direction、Evidence、reason、
why_score_is_insufficient、base_decision、candidate_decision、scope、plan_idを保存する。
低RRはrr_rationale、代替Entry、取り逃しリスク、前提失効条件を必須とする。
Severe条件判断には全対象findingごとの理由・残リスク・解消条件を保存し、ApprovalRecordを参照。
不存在Evidence、反証隠し、対象時点不一致なら採用しない。

## 6. マクロ・決算・履歴
マクロはsector → sector_condition → drivers → company_sensitivity → specific_factors → dominant_force。
直接の一律加減点は禁止。反証と時間軸も保持。
跨ぎ方針未入力は跨ぐ／跨がないを両表示。決算日不明なら推測しない。
上段に状態・結論・二重スコア・信頼度・重要警告・承認状態、詳細に価格戦略とEvidenceを表示する。
買う／待つ理由はそれぞれ最大3点。通常損切、最終損切、価格と無関係な撤退条件を分離する。
分析時点の入力・データ・採点基準選択・実AI出力・規則版を保存し、過去結果を更新しない。
人間比較は最終判断、同時間軸の銘柄順位、主要理由を優先する。数値完全一致を目標にしない。

## 7. 重大度選択の初期ガイド
重大度の選択にもEvidenceと理由が必須。次を初期の判定基準として用いる。
- 解消不能な銘柄／時点／価格調整矛盾、必須の前提資料欠落で対象評価が成立しない：Critical。
- 確認できる不正・会計疑義、継続企業懸念、重大希薄化・失注等で投資前提の再点検が必要だが評価自体は可能：Severe。
- 流動性の著しい不足で実際の売買条件に重大制約が確認できる：Severe。取引停止等で有効Entry自体が作れないならEntry側Critical。
- 決算接近、限定的な流動性制約、企業感応度を介した逆風、確認可能な補助データ遅延：Warningまたは該当の暫定状態。
重大度をイベント名・単一数値だけで確定せず、影響範囲と確認事実を示す。
根拠が曖昧で重大度を決められない場合は要確認として対象判断を暫定に保ち、Warningで問題なし扱いにしない。
